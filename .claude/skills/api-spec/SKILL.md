# API 規格撰寫規範

用途：以「模組」為單位，產出給前端串接用的精簡規格。規格說明「應該怎麼運作」，不含測試過程與負面案例。
動手前先讀專案的 `AGENTS.md` 或 `CLAUDE.md`、需求文件與現有實作；模組、路由、服務代號、錯誤碼一律以專案實際內容為準，不憑記憶。
格式刻意精簡，不自行增加章節。一個模組一份檔案，存放於專案的 `docs/api/{模組}.md`；已存在時不覆寫，改存新檔或在檔內新增版本區塊。

## 文件結構（依序）

1. **基本資訊**：模組、日期與負責人、需求來源、範圍。
2. **共通約定**：驗權方式、請求與回應格式、成敗判斷依據。各 API 相同的內容只寫這一處。
3. **操作項目表**：每支 API 一列，欄位為「操作／說明／方法與路徑／服務代號與優先序」，取自需求文件。
4. **各 API 明細**：每支 API 一個區塊，固定順序為：
   - 標題：`【操作名稱（服務代號）】`
   - PATH：方法與路徑
   - REQ：一個成功案例的 JSON，用 `//` 註解標示必填與限制
   - RSP：對應的成功回應 JSON
   - 錯誤碼表：錯誤碼、說明、常數名稱
   - 備註：前置條件、副作用、與舊系統差異（無則省略）

## 撰寫規則

1. **每支 API 只放一個成功案例**，不放負面案例與測試判定；負面案例屬於測試，另行記錄。
2. 規格與現有實作或需求不一致時，**先判斷哪邊錯**：實作有誤以需求為準，並在備註標示「現況落差」；需求推導有誤則更正規格。涉及舊系統刻意保留的行為，先與負責人確認。
3. 錯誤碼只列該 API 實際會回的，查專案的錯誤碼定義，不另行發明。
4. 範例一律使用虛構資料，以 `test_` 或 `TEST_` 為前綴；權杖、密碼、金鑰、連線字串不得出現完整值，只保留前 4 碼加 `****`。
5. 過長的回應（約 50 行以上）可截斷並註明「已省略 N 筆」。
6. 新增與修改共用同一入口時，合併說明並註明判斷依據。
7. 未實作或僅有空殼的 API 仍列入，備註註明「尚未實作」。
8. 同一欄位在多支 API 出現時，名稱與說明保持一致。
9. 副作用（寫入、延長期限、新增紀錄）要在備註說明。
10. 以繁體中文撰寫，欄位名、路徑、JSON、技術名詞保留英文。
11. 只寫對外可見的行為，不寫內部結構（類別、函式、資料表、框架用語）。

## 產出前自檢

- 服務代號與路徑和需求文件一致，API 數量與實作相符。
- 每支 API 都有 PATH、REQ、RSP、錯誤碼。
- 所有現況落差都已標示。
- 範例無機敏資料，副作用已說明。
