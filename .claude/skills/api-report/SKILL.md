# API 測試報告規範

用途：測完 API 後，產出簡易、好讀的測試報告。以「模組」為單位，一個模組一份報告、一張 issue。
動手前先讀專案根目錄的 `CLAUDE.md` 與需求文件，模組清單、路由、服務代號、錯誤碼定義皆以專案實際內容為準，不憑記憶。
格式刻意精簡，不自行增加章節。

## 報告結構（依序）

1. **基本資訊**：Issue 編號、測試日期與人員、Commit 完整 hash、環境（基底網址、資料庫主機與名稱、快取是否啟用）。資料庫不寫帳密。
2. **涉及的操作項目**：每支 API 一列，欄位為「操作／說明／對應 API／服務代號與優先序」，內容取自需求文件。需求標已完成但實際為空殼者，於備註註明。
3. **各 API 測試明細**：每支 API 一小節，固定順序為 PATH、REQ、RSP、備註（無則省略）、錯誤碼表。

不需要測試摘要、缺陷清單、未測項目章節，由後續 review 另行處理。

## 明細寫法

- REQ／RSP 以成功案例為主；JSON 可用 `//` 註解標示必填與限制（僅供文件，實際送出不含註解）。
- 錯誤碼表列出該 API 實際會回的錯誤碼、說明與對應常數，查專案的錯誤碼定義。
- 實際回應與預期不符時，補貼該案例的 REQ、預期 RSP、實際 RSP，讓讀者不用重跑就能看出差異。
- 每支 API 盡量涵蓋：成功、必填缺漏、格式錯誤、權杖缺失或無效、查無資料、重複新增；不適用的省略。
- 空殼 API（無實作、只回空物件）：REQ 帶空物件，RSP 貼實際回應，備註註明「尚未實作」。

## Issue 規範

- 標題：`[測試] {模組名} API 測試`；標籤：`test`、`module::{模組名}`。
- 發現缺陷另開子 issue，標題 `[缺陷] {服務代號} {簡述}`，並於測試 issue 加 `bug` 標籤。

## 必守規則

1. REQ／RSP 必須是實際執行結果，不可改寫或編造；過長（約 50 行以上）可截斷並註明「已省略 N 筆」。
2. 測試資料一律以 長`test_` 或 `TEST_` 為前綴，寫入類測試完成後清除。
3. 只測測試環境；不確定連到哪個資料庫時先停下確認，不執行寫入測試。
4. 驗權類功能優先測負面案例（無權杖、已失效權杖仍能存取），快取開、關各測一次。
5. 報告以繁體中文撰寫，欄位名、JSON、技術名詞保留英文。

## 產出前自檢

- 服務代號、路徑與需求文件一致，API 數量與實作相符。
- 所有與預期不符的案例都有預期／實際 RSP。
- 機敏資料已遮罩。
