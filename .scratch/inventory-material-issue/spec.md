# 領料單（內部領用出庫）與庫存異動紀錄

Status: ready-for-agent

相關文件：`GLOSSARY.md`（術語以此為準）、`docs/adr/0001`（簽核動作與同一交易）、`docs/adr/0002`（異動不建品項主檔）。

## Problem Statement

目前庫存只有一條路徑會改變數量：進貨單簽核完成後增加庫存。公司內部領用物料（專案施工、維修、樣品、自用）沒有任何單據可以記錄，也沒有簽核，庫存數量只能靠人工修改資料庫；庫存數量為何變動、誰改的、依據哪張單，完全無法追查。

另外，現有進貨單的庫存更新不是原子的（簽核已存檔、庫存才更新，失敗時兩邊不一致），且簽核引擎的通用端點可以繞過模組邏輯，所以領料單不能照搬進貨單的做法。

## Solution

提供**領料單**：倉管或有權限的人建立領料單，選擇庫位、領料人、領料用途與要領用的庫存項目與數量，送出簽核；簽核全部通過的那一刻才扣減庫存。簽核期間不預留數量。已核准的領料單可由最後一關的簽核人作廢，作廢時庫存回補。

同時新增**庫存異動紀錄**：每一次庫存數量的增減（進貨入庫、進貨作廢、領料出庫、領料作廢）都留下一筆紀錄，包含來源單據、異動前後數量、操作人與時間，並提供唯讀查詢。進貨單的核准與作廢也接上異動紀錄。

庫存永遠不得為負；核准、扣庫存與寫異動在同一個交易內完成，失敗全部回滾；庫存表加上樂觀並發控制，避免兩張單同時核准互相覆蓋。

## User Stories

### 建立與維護領料單

1. 身為倉管，我想建立一張領料單並指定庫位，以便記錄這次要從哪個庫位領料。
2. 身為倉管，我想在領料單中選擇領料人（在職員工），以便代替他人建單時仍能記錄實際領走物料的人。
3. 身為倉管，我想選擇領料用途（專案領用、維修、樣品、自用、其他），以便事後能依用途分類統計。
4. 身為倉管，我想在領料單上選填客戶與專案名稱，以便專案領用時能追溯到對應的客戶與專案。
5. 身為倉管，我想填寫領料日期（預設今天），以便記錄實際領料的日子，而不是簽核完成的日子。
6. 身為倉管，我想在領料單上寫備註，以便說明特殊情況。
7. 身為倉管，我想從指定庫位的庫存項目中挑選要領用的項目，並看到品名、供應商、庫位與現有數量，以便精準選到要扣的那一筆庫存。
8. 身為倉管，我想為每個明細填寫領用數量（可含小數），以便記錄實際領用量。
9. 身為倉管，我想在同一張領料單內不會重複出現同一個庫存項目，以便避免同一項目被重複計算；要領兩次就合併成一行。
10. 身為倉管，我想在儲存草稿時看到庫存不足的警告，以便提早知道數量可能不夠，但仍能先保留草稿。
11. 身為倉管，我想領料單建立時自動取得單號（`IS` + 民國年月 + 三位流水），以便每張單據都有唯一編號。
12. 身為倉管，我想編輯草稿狀態的領料單，以便修正填錯的內容。
13. 身為倉管，我想編輯被退回的領料單後重新送簽，以便處理簽核人的意見。
14. 身為倉管，我想刪除草稿狀態的領料單，以便清掉不需要的草稿。
15. 身為倉管，我想在領料單進入簽核中、已核准或已作廢後無法編輯或刪除，以便單據內容不會在簽核後被偷偷更動。
16. 身為倉管，我想被擋下時看到明確的錯誤訊息（例如「簽核中的領料單不可編輯」），以便知道原因。

### 送簽與簽核

17. 身為倉管，我想把草稿送出簽核，以便讓主管審核這次領料。
18. 身為倉管，我想在送簽時被告知庫存不足的品項與缺少的數量，以便先調整再送。
19. 身為倉管，我想在簽核流程尚未完成前撤銷送簽，以便發現錯誤時能收回，撤銷後單據變成已退回。
20. 身為簽核人，我想看到待我簽核的領料單內容（庫位、領料人、用途、明細與數量），以便做出核准或拒絕的決定。
21. 身為簽核人，我想核准領料單，以便讓領料生效並自動扣庫存。
22. 身為簽核人，我想拒絕領料單並寫下原因，以便讓倉管知道為什麼被退回，拒絕後單據變成已退回。
23. 身為簽核人，我想在最後一關核准時，若庫存已不足，核准被拒絕並列出不足的品項與數量，以便不會讓庫存變成負數。
24. 身為簽核人，我想在核准因庫存被別張單同時扣走而衝突時，看到「庫存已被異動，請重新操作」，單據仍維持簽核中，以便我稍後重試。
25. 身為簽核人，我想在核准失敗時簽核紀錄也一併回復，以便不會出現「已核准但庫存沒扣」的單據。
26. 身為簽核人，我想核准中間關卡時不影響庫存，以便只有最後一關通過才真正扣庫存。
27. 身為最後一關簽核人，我想作廢已核准的領料單，以便在領料作業有誤或物料沒真的領走時沖回庫存。
28. 身為最後一關簽核人，我想作廢後庫存自動回補並留下反向異動，以便庫存與紀錄一致。
29. 身為倉管，我想作廢後的領料單不能再重送，以便保持歷史單據的完整性；要重領就另開新單。
30. 身為倉管，我想無法透過通用簽核端點對領料單進行簽核動作（送簽、核准、拒絕、撤銷、作廢），以便所有動作都經過領料單自己的邏輯。
31. 身為簽核人，我想仍能透過通用簽核紀錄與通知查看領料單的簽核進度，以便知道單據走到哪一關。

### 查詢與匯出

32. 身為倉管，我想依單號、領料用途、領料人、庫位、客戶名稱、專案名稱、狀態與領料日期區間查詢領料單，以便快速找到單據。
33. 身為倉管，我想領料單列表支援排序與分頁，以便在資料很多時仍能瀏覽。
34. 身為倉管，我想查看單張領料單的完整內容與簽核進度，以便了解單據現況。
35. 身為主管，我想把領料單列表匯出成 Xlsx 或 PDF（單頭資訊），以便做月報或存檔。
36. 身為主管，我想匯出結果與畫面上的查詢條件一致，以便報表數字可信。

### 庫存異動紀錄

37. 身為庫存管理員，我想每次庫存增減都留下一筆異動紀錄，以便事後追查數量為什麼變動。
38. 身為庫存管理員，我想異動紀錄包含異動類型（進貨入庫、進貨作廢、領料出庫、領料作廢），以便區分原因。
39. 身為庫存管理員，我想異動紀錄包含來源單據（類型與單號），以便回頭找到依據的單據。
40. 身為庫存管理員，我想異動紀錄包含異動數量（增加為正、減少為負）以及異動前後的數量，以便核對庫存帳。
41. 身為庫存管理員，我想異動紀錄記錄操作人與異動時間（核准或作廢當下），以便稽核。
42. 身為庫存管理員，我想依庫存項目、異動類型與日期區間查詢異動紀錄，以便檢視單一庫存項目的歷程。
43. 身為庫存管理員，我想進貨單核准入庫與作廢時也留下異動紀錄，以便庫存的所有變動來源都被記錄。
44. 身為庫存管理員，我想異動紀錄是唯讀的，以便歷史不會被竄改。

### 權限與維運

45. 身為系統管理員，我想有「領料單檢視、編輯、刪除」三種權限可指派給角色，以便控管誰能看、建、刪領料單。
46. 身為系統管理員，我想有檢視權限的人能看到所有人的領料單，以便倉管與主管能互相查核。
47. 身為系統管理員，我想領料單每個 API 都檢查權限，以便沒有權限的人無法呼叫。
48. 身為系統管理員，我想在簽核設定中建立領料單的簽核流程（最後一關用指定人員模式），以便領料單能送簽並能被作廢。
49. 身為系統管理員，我想在尚未設定領料單簽核流程時，送簽得到明確錯誤，以便知道需要先設定。
50. 身為系統管理員，我想能維護領料用途的選項，以便未來新增用途時不用改程式。
51. 身為系統管理員，我想有可重複執行的 SQL 腳本建立領料用途初始資料，以便各環境部署一致。
52. 身為開發者，我想有自動化測試涵蓋領料單的扣庫存、不足拒絕、作廢回補與交易回滾，以便日後修改不會破壞庫存數量的正確性。

## Implementation Decisions

### 領域模型與術語

- 遵循 `GLOSSARY.md`：庫存項目、庫位、庫存異動、進貨單、領料單、出貨單、領料人、出庫、領料用途、領料單狀態、作廢。
- 本次只做領料單；出貨單（對客銷售）不在範圍，`TableType.出貨單 = 8` 保留。新增 `TableType.領料單 = 9`。
- 領料單狀態共五種：草稿、簽核中、已核准、已退回、已作廢。不使用進貨單的 `IsApproval` 布林值。

### 領料單狀態轉換

- 草稿 → 送簽 → 簽核中。
- 簽核中 → 最後一關核准 → 已核准（同時扣庫存、寫異動）。
- 簽核中 → 拒絕 → 已退回；簽核中 → 撤銷 → 已退回。
- 已退回 → 編輯 → 可再次送簽 → 簽核中。
- 已核准 → 作廢 → 已作廢（回補庫存、寫反向異動）。已作廢為終態，不可重送、不可編輯。
- 可編輯：草稿、已退回。可刪除（實際刪除）：僅草稿。

### 資料結構

- 新增領料單單頭與明細兩張資料表（模組編號 4030）。單頭：單號、領料日期、領料用途、庫位、領料人（員工識別碼）、客戶（選填）、專案名稱（選填）、備註（選填）、狀態、建單人、建單時間。明細：領料單、庫存項目識別碼、數量，以及料號、品名、單位的快照。明細對庫存項目為一般外鍵，不串聯刪除。
- 新增庫存異動紀錄資料表（模組編號 4040）：庫存項目、異動類型、來源單據類型與單號、異動數量（帶正負）、異動前數量、異動後數量、操作人、異動時間。
- 庫存表新增 `RowVersion` 欄位，作為樂觀並發控制。
- 新增領料用途的 `SystemConfig` 類別（`MaterialIssuePurpose`），初始資料：專案領用、維修、樣品、自用、其他；另提供可重複執行（先檢查是否存在）的 SQL 腳本。
- 資料庫專案與 EF 實體模型需同步更新。
- 新增列舉：領料單狀態、庫存異動類型（進貨入庫、進貨作廢、領料出庫、領料作廢）；`TableType` 新增領料單；`PermissionType` 新增 `領料單檢視 = 4030`、`領料單編輯 = 40300`、`領料單刪除 = 40301`。

### 領料單服務與簽核（見 ADR 0001）

- 領料單服務提供：查詢列表、取得單筆、新增、編輯、刪除、匯出列表、送簽、核准、拒絕、撤銷、作廢；以及領料用途下拉、在職員工下拉（若現有員工下拉未限制在職）。新增與編輯共用同一個修改邏輯（遵循專案後端風格）。
- 五個簽核動作（送簽、核准、拒絕、撤銷、作廢）都由領料單自己的端點處理：呼叫簽核引擎、更新單據狀態、必要時增減庫存與寫異動，全部在單一資料庫交易內完成；失敗全部回滾，包含引擎已寫入的簽核紀錄。
- 通用簽核控制器對領料單的上述五個動作直接回錯誤（訊息指示由領料單功能操作）；讀取類（簽核進度、通知）不受影響。進貨單等其他單據不在此限。
- 新增 `MaterialIssueApprovalTargetHandler` 並註冊到簽核引擎；簽核紀錄的單據識別以單號為準。
- 簽核流程為資料，不內建預設流程；未設定時沿用引擎既有錯誤「找不到啟用中的簽核設定」。
- 作廢沿用引擎規則：僅最後一關簽核人本人可作廢；以角色模式設定的關卡實際上無法作廢，列為已知問題，規格要求最後一關使用指定人員模式。
- 單號由既有序號服務產生，前綴 `IS`。

### 庫存規則

- 簽核完成才扣庫存，不做預留量。庫存不得為負。
- 檢查時機：儲存草稿時，不足僅回傳警告、仍可儲存；送簽時，不足則拒絕送簽並列出不足的品項與數量；最後一關核准時再檢查一次，不足則拒絕核准、單據維持簽核中。
- 並發：以 `RowVersion` 偵測衝突；衝突時拒絕核准並回傳「庫存已被異動，請重新操作」，單據維持簽核中、整個交易回滾。
- 作廢回補為加數量，不需要不足檢查；一律寫反向異動。
- 異動時間記核准（或作廢）當下，不使用領料日期；操作人為最後核准人（或作廢人）。

### 進貨單（最小改動，見 ADR 0002）

- 進貨單核准入庫與作廢時，同步寫入異動紀錄（進貨入庫、進貨作廢），與庫存更新在同一次儲存內。
- 因庫存表新增 `RowVersion`，進貨入庫與作廢路徑需將並發衝突轉成友善錯誤，而非未處理例外。
- 其餘進貨單問題一律不修，見「已知問題」。

### 異動紀錄與庫存查詢

- 提供唯讀異動查詢（依庫存項目、異動類型、日期區間篩選，支援排序與分頁，遵循專案查詢慣例）；不提供匯出，不提供任何寫入端點。
- 異動不補寫歷史；上線前的庫存視為期初。異動直接關聯庫存項目，不建立品項主檔。
- 為了讓領料時能選庫存項目，庫存查詢需能依庫位識別碼篩選（現有以庫位名稱篩選）。

### 權限、查詢、匯出

- 領料單每個 API 都掛權限檢查（檢視、編輯、刪除對應新增的三個權限）；簽核與作廢的權限由簽核引擎的簽核人設定決定，不另開權限。有檢視權限者可看到所有領料單。
- 查詢條件：單號（包含）、領料用途（相等）、領料人（包含）、庫位（相等）、客戶名稱（包含）、專案名稱（包含）、狀態（相等）、領料日期起迄。
- 匯出：Xlsx 與 PDF 列表，只含單頭資訊；與列表共用同一個 EF 查詢，不使用預存程序；沿用共用查詢模板與既有匯出輔助。
- 遵循專案後端風格：薄 Controller、服務回傳統一結果模型、Swagger 標註與分組、操作紀錄屬性。

## Testing Decisions

- 好的測試只驗證外部可觀察行為（回傳結果、資料庫中的單據狀態、庫存數量、異動紀錄內容），不驗證內部實作細節。
- **主縫**：領料單服務的公開方法。測試使用真實的 `ERPDbContext`（SQLite in-memory）、真實的簽核引擎與序號服務，只替換「目前登入者」，可切換簽核人與角色。涵蓋：狀態轉換與編輯/刪除限制、送簽與核准時的不足檢查、核准扣庫存與異動內容、不足時拒絕核准且簽核紀錄一併回滾、拒絕與撤銷後變成已退回並可編輯重送、作廢回補與反向異動、作廢後不可重送、無簽核設定時送簽失敗、非最後簽核人不可作廢、明細規則（數量大於 0、不重複）。異動內容透過異動查詢服務驗證。
- **輔助縫一**：進貨單服務（既有），只驗證核准入庫與作廢時有寫入異動，兼作回歸檢查。
- **輔助縫二**：通用簽核控制器，驗證對領料單的五個簽核動作回錯誤且資料庫不變，對其他單據不受影響。
- 並發衝突：SQLite 不會自動更新 `RowVersion`，測試專案提供 `SaveChanges` 攔截器模擬其遞增，並在核准路徑寫庫存之前以另一個連線插入競爭寫入，強制產生並發例外，驗證「衝突被轉成友善錯誤、整個核准回滾」。SQL Server 上 `rowversion` 欄位的實際自動遞增無法在 SQLite 驗證。
- 新增獨立的測試專案（xUnit）。專案目前沒有任何測試，無既有範本可循，需要同時建立測試基礎設施（資料庫建立、登入者替身、攔截器）。

## Further Notes

### 規格中的解讀

- 原決策「建單與送簽時先檢查並提示」，本規格解讀為：草稿儲存僅警告、可儲存；送簽時不足則拒絕。若期望送簽也只警告，請在實作前回報。

### 上線前置作業

1. 執行領料用途初始資料的 SQL 腳本。
2. 在簽核設定建立「領料單」的啟用中簽核流程，最後一關使用指定人員模式。
3. 在角色權限中指派領料單檢視、編輯、刪除（包含倉管角色）。
4. 部署資料庫變更（新資料表、`RowVersion`）。

### 已知問題（記錄，不在本次修正）

- 進貨單：`Edit` 無狀態檢查，核准後被編輯再作廢會造成扣回數量與入庫數量不一致；`IsApproval` 作廢後未重設；核准入庫時 `Total` 與 `LastPurchaseDate` 未更新；核准與入庫不是同一個交易；Controller 未掛權限檢查（庫存 Controller 同樣）。
- 通用簽核端點可繞過進貨單的庫存更新。
- 簽核引擎：`OnApprovedAsync` 與 `OnVoidedAsync` 鉤子已宣告但從未被呼叫；角色模式的關卡因核准時未記錄簽核人而無法作廢。
- 庫存匯出使用的預存程序，WHERE 條件缺少括號，過濾結果不正確。
- 專案目前沒有任何測試專案。
