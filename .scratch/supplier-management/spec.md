# 供應商管理（供應商主檔與進貨單串接）

Status: resolved

> 三張 ticket 皆為 resolved。SQL 部署腳本、權限端點與前端畫面仍待使用者在真實環境驗證，細節見各 ticket 的 Comments；進貨單前端因專案尚無頁面而延後（後端 API 已就緒）。

相關文件：`GLOSSARY-MAP.md`（庫存管理 context，術語以 `docs/inventory/GLOSSARY.md` 為準：供應商、供應商編號、停用（供應商））、`docs/inventory/adr/0003`（進貨單與庫存項目只記供應商外鍵，不存名稱快照）、`docs/inventory/adr/0002`（庫存以供應商＋庫位＋料號為單位）、`docs/company/adr/0001`（公司主檔的同型決策，供應商比照）。範本參考 `.scratch/company-management/spec.md`。

## Problem Statement

資料庫已有供應商資料表（`t_4060Supplier`），被庫存項目與進貨單以外鍵引用，但沒有任何維護功能：不能新增、編輯、停用或刪除供應商，只有一個把全部供應商列成下拉選單的查詢，掛在通用的 `SharedController` 上、沒有權限限制。進貨單儲存時也完全不驗證供應商，選到不存在或不該再使用的供應商都不會被擋下。

## Solution

提供**供應商管理**：有權限的人可以新增、編輯、停用與啟用、刪除**供應商**，並在列表與詳情檢視。填進貨單用的下拉選單只列啟用中的供應商，並受權限控管。

被進貨單或庫存項目引用過的供應商不能刪除，只能**停用**；停用後不再出現在新進貨單的選項，但歷史進貨單與既有庫存項目仍顯示原供應商。單據只記供應商外鍵，供應商改名、改統編視為更正，歷史資料跟著顯示新值（ADR-0003）。

進貨單只做三處串接：下拉選單、儲存時檢查供應商存在、送簽時檢查供應商是否已停用。不改庫存、付款、應付與簽核流程。

## User Stories

### 供應商主檔維護

1. 身為庫存管理者，我想新增一間供應商，以便進貨單可以選到它。
2. 身為庫存管理者，我想填寫供應商編號與名稱，以便記錄供應商的必要資料。
3. 身為庫存管理者，我想選填統一編號、負責人、聯絡電話、傳真、業務人員、地址、銀行名稱、分行名稱、支票帳號、匯款帳號、付款天數與信用額度，以便把非必要資料也留存。
4. 身為庫存管理者，我想未填必填欄位或超過欄位長度時被擋下，以便資料符合資料表的限制。
5. 身為庫存管理者，我想供應商編號在所有供應商之間不可重複，重複時被擋下並看到明確訊息，以便編號能唯一識別供應商。
6. 身為庫存管理者，我想統一編號選填，但有填就必須是 8 碼數字，以便不會存入格式錯誤的統編。
7. 身為庫存管理者，我想統一編號有填時在所有供應商之間不可重複，重複時被擋下並看到明確訊息，以便一個法人實體不會有兩筆資料。
8. 身為庫存管理者，我想供應商名稱可以重複，以便不同編號的同名據點或舊廠商能並存。
9. 身為庫存管理者，我想付款天數以整數天數填寫，以便語意明確。
10. 身為庫存管理者，我想編輯既有供應商的資料，包含已被進貨單或庫存項目引用的供應商，以便更正錯字、編號或統編。
11. 身為庫存管理者，我想供應商被引用後仍可修改編號與統編，以便更正而不是換一間供應商（歷史單據跟著顯示新值）。
12. 身為庫存管理者，我想新增的供應商預設為啟用中，以便立刻可以被選用。
13. 身為庫存管理者，我想停用一間供應商，以便它不再出現在新進貨單的選項。
14. 身為庫存管理者，我想重新啟用一間已停用的供應商，以便恢復它的使用。
15. 身為庫存管理者，我想可以停用或刪除最後一間啟用中的供應商，以便不受「至少保留一間」的限制（沒有啟用中供應商只是無法新增進貨單）。
16. 身為庫存管理者，我想刪除一間從未被進貨單或庫存項目引用過的供應商，以便清掉誤建的資料。
17. 身為庫存管理者，我想刪除被進貨單或庫存項目引用過的供應商時被擋下，並提示改用停用，以便歷史資料不會失去供應商。
18. 身為庫存管理者，我想在列表看到供應商編號、名稱、統一編號、負責人、聯絡電話與啟用狀態，以便快速找到供應商。
19. 身為庫存管理者，我想列表可用關鍵字（編號、名稱、統一編號）與啟用狀態篩選，以便縮小範圍。
20. 身為庫存管理者，我想列表預設把啟用中的供應商排在前面，再依供應商編號排序，以便常用的先看到。
21. 身為庫存管理者，我想檢視單一供應商的詳細資料，以便確認銀行、帳號與信用額度。
22. 身為管理者，我想供應商的新增、編輯、停用、啟用、刪除都寫入操作紀錄，以便事後追查。
23. 身為管理者，我想供應商的維護不需要簽核，以便有權限的人可以直接操作。

### 權限

24. 身為管理者，我想有「供應商檢視」權限的人才能進入供應商管理頁並看到列表與詳情，以便控管誰能看供應商資料。
25. 身為管理者，我想有「供應商編輯」權限的人才能新增、編輯、停用與啟用供應商，以便控管誰能改主檔。
26. 身為管理者，我想有「供應商刪除」權限的人才能刪除供應商，以便刪除權限獨立於編輯。
27. 身為進貨單建單人，我想不需要供應商檢視權限，就能在進貨單的下拉選單看到啟用中的供應商，以便我能填單。
28. 身為管理者，我想沒有「進貨單編輯」也沒有「庫存編輯」權限的人無法取得填單用的供應商選單，以便供應商資料不外流給與填單無關的人。

### 進貨單串接

29. 身為進貨單建單人，我想下拉選單只列出啟用中的供應商，並同時顯示供應商編號與名稱，以便不會選到已停用的供應商，也分得出同名的供應商。
30. 身為進貨單建單人，我想編輯草稿或已退回的進貨單時，若原供應商已被停用，仍看得到它並標示「已停用」，以便知道原值是什麼。
31. 身為進貨單建單人，我想送簽時若所選供應商已停用就被擋下並提示改選，以便停用的供應商不會被新進貨單使用。
32. 身為進貨單建單人，我想儲存進貨單時若供應商不存在就被擋下並看到明確訊息，以便不會因外鍵錯誤得到系統錯誤。
33. 身為簽核人，我想已送簽或已核准的進貨單，即使供應商後來被停用，簽核與核准仍照常進行並增加該供應商的庫存項目數量，以便停用不影響進行中的單據。
34. 身為庫存使用者，我想歷史進貨單與庫存項目在供應商停用後仍顯示原供應商，供應商改名後顯示新名稱，以便資料前後一致（ADR-0003）。

### 既有資料與上線

35. 身為系統維護者，我想部署時既有供應商預設為啟用中，以便上線後原本的進貨與庫存不受影響。
36. 身為系統維護者，我想既有供應商若名稱為空，部署腳本先補成佔位名稱（例如「（未命名供應商 {Id}）」）再把名稱改為必填，以便不會因空名稱而失敗，且事後能在管理頁更正。
37. 身為系統維護者，我想既有的付款天數（原為日期型別，內容無法可靠轉成天數）部署時被清空後改成整數型別，以便語意正確。
38. 身為系統維護者，我想部署前能先查出重複的統一編號，腳本只列出衝突、不自動修改，也不建立唯一索引，由人工處理後再補，以便不會誤改真實資料。
39. 身為系統維護者，我想部署腳本可重複執行而不重複加欄位或索引，以便誤跑第二次也安全。

## Implementation Decisions

- **沿用現有供應商資料表**：不另建新表。新增啟用旗標（預設啟用）；供應商名稱改為必填；付款天數由日期型別改為整數；供應商編號改為必填並建唯一索引（取代現有非唯一索引）；統一編號建「有值時唯一」的篩選唯一索引。信用餘額、最後交易日、暫付金額欄位保留，但本次不開放編輯也不顯示。實體模型與資料庫專案同步更新，並依專案慣例在 `docs/sql/` 提供既有資料庫的部署腳本。
- **供應商編號必填的既有資料問題**：既有資料的供應商編號可能為空或重複；部署腳本與統編一樣，只列出衝突，由人工處理後再補唯一索引，不自動編造編號。（編號欄位在腳本中先維持原狀，驗證規則在服務層先行生效。）
- **部署腳本順序**（可重複執行）：(1) 新增啟用旗標；(2) 補空名稱後改 NOT NULL；(3) 付款天數清空後改整數；(4) 列出重複與空白的編號、重複的統編，無衝突時才建立唯一索引。
- **供應商服務與端點**：擴充現有 `_4060SupplierService`（列表、取得單筆、新增、編輯、停用、啟用、刪除、填單用選單），新增 `_4060SupplierController`，列表使用既有的排序與分頁慣例。填單用選單可指定一個供應商 Id，使該供應商即使已停用也一併回傳並標示已停用，供編輯草稿顯示原值。
- **選單端點搬移**：填單用選單改走供應商專屬端點並要求「進貨單編輯」或「庫存編輯」其中之一，不要求供應商檢視。`SharedController.GetSupplierSelect` 暫時保留以免破壞現有呼叫，但改為只回傳啟用中的供應商；待確認無人使用後再移除。
- **權限**：沿用已存在的供應商檢視（4060）、供應商編輯（40600，含停用與啟用）、供應商刪除（40601）。
- **停用與刪除規則**：刪除時若任一進貨單或庫存項目引用它就擋下並提示改用停用；停用與刪除都不設「最後一間」限制。新增、編輯、停用、啟用、刪除寫入現有的操作紀錄機制；供應商維護不走簽核。
- **進貨單規則**：儲存（新增與編輯）時檢查供應商存在；送簽時檢查供應商是否啟用中，已停用就擋下並提示改選；已送簽、已核准的進貨單不受之後的停用影響，核准流程與庫存增加不變。只補「存在」與「送簽時啟用」兩項檢查，不改其他進貨單驗證與簽核引擎流程。
- **列表欄位**：供應商編號、名稱、統一編號、負責人、聯絡電話、啟用狀態；篩選為關鍵字（編號、名稱、統一編號）與啟用狀態；預設啟用中優先，再依供應商編號。
- **前端**：新增供應商列表頁與編輯頁（新增、編輯、停用與啟用、刪除、篩選），新增路由與選單入口並依權限顯示，比照 `CompanyList.vue`、`CompanyEdit.vue` 與 `companyApi.js`；依專案前端規範撰寫。專案目前沒有進貨單與庫存頁面，進貨單的前端串接本次延後，只提供後端 API。
- **文件**：詞彙表（供應商、供應商編號、停用（供應商））與 ADR-0003 已建立；實作中若出現新術語，更新 `docs/inventory/GLOSSARY.md`。

## Testing Decisions

- **好測試的標準**：只驗證對外可觀察的行為（回傳結果、資料庫內容、單據狀態），不驗證內部實作；一個測試對應一個使用者故事或規則。
- **接縫：服務層。**
  - 新增供應商服務測試檔：覆蓋新增、編輯、必填與長度驗證、供應商編號唯一、統編格式與唯一、名稱可重複、被引用後仍可改編號與統編、停用與啟用、刪除與被進貨單或庫存項目引用的保護、可停用或刪除最後一間、填單用選單（只列啟用中、指定已停用供應商時一併回傳）、列表篩選與排序。
  - 延伸進貨單服務測試：覆蓋儲存時供應商不存在被擋下、送簽時供應商已停用被擋下、已送簽與已核准的進貨單不受停用影響。
- **既有測試與種子資料**：供應商欄位必填與編號必填後，共用種子資料需帶供應商編號與名稱，既有測試才能建立供應商；屬種子資料調整，不是新接縫。
- **前例**：公司服務測試、領料服務測試與進貨單服務測試（記憶體資料庫、假簽核引擎、假使用者、假流水號、種子資料）。
- **不做**：前端目前沒有自動化測試設定，本次不新增，前端只做建置驗證與手動驗證。
- **限制**：測試使用 SQLite 記憶體庫，不等於 SQL Server。篩選唯一索引、型別轉換、部署腳本的重複執行，以及列表查詢，須由使用者在真實資料庫驗證。

## Out of Scope

- 進貨單前端頁面與庫存前端頁面（專案目前沒有）。
- 信用餘額、最後交易日、暫付金額的維護與顯示（待日後有應付或付款功能時再接）。
- 供應商與客戶、公司之間的關聯。
- 供應商主檔的簽核。
- 進貨單與庫存項目上的供應商名稱快照（ADR-0003 已決定不做）。
- 品項主檔與同品項多供應商（ADR-0002 已決定先不做）。
- 供應商匯入、匯出與報表。
- 前端自動化測試。

## Further Notes

- 「供應商」指我方向其取得物料的對象，不是客戶，也不是我方旗下的公司；程式與畫面請避免用「廠商、賣方」稱呼。
- 進貨單「送簽」的入口已確認（ticket 02）：`_4010PurchaseService.SendApproval`；進貨單沒有狀態欄位（只有 `IsApproval`），停用檢查加在呼叫簽核引擎之前。
- 實作時需確認 `t_1201PettyCashDetail.Supplier`（字串欄位）是否仍與供應商資料表無關；目前判斷無關，不納入本次。
- 供應商編號必填與唯一的規則，在既有資料有空白或重複時，需要使用者先處理資料才能建立索引；這是部署前的人工步驟，不是程式缺陷。
