## Comments

### 驗證清單（由 agent 整理，供使用者手動執行；agent 不判定通過）

前置：ticket 01–07 已實作，工作樹尚未 commit；後端 `ERP.Tests` 完整 276 項通過（SQLite 記憶體庫）。以下是記憶體庫驗證不了、必須在真實環境確認的項目。

**A. 資料庫**
1. 在既有 SQL Server 執行 `document/sql/出差單資料表.sql`（可重複執行）；新環境以 ERP.DB 專案發佈。
2. 確認 `t_1060BusinessTrip` 的 `StartDate`、`EndDate` 為 `DATE`、`No` 有唯一索引、`CK_t_1060BusinessTrip_Dates` 存在。
3. 確認實體模型與 DbContext（agent 手寫，非 scaffold 產出）與實際資料表一致；有空可重新 scaffold 比對。

**B. 權限與簽核設定**
4. 在角色權限設定勾選「出差單」（PageId 1060）給可建單的角色；勾選「出差單管理」（PageId 1061）給需要看全部的角色。確認重新登入後 JWT 的 `permissions` 帶出 1060。
5. 以現有簽核設定 API 建立一組啟用的「出差單」設定（`TableType` = 10，先 `CreateSettings` 再用現有流程設定關卡），分別試「指定人員」與「指定角色」兩種關卡。確認只有一組啟用；有多組啟用時送簽會回設定重複的錯誤。
6. 確認沒有啟用設定時，送簽回「找不到啟用中的簽核設定」。

**C. 流程（手動走完，前端與後端都要看）**
7. 建單 → 送簽 → 逐關核准到已核准。
8. 建單 → 送簽 → 簽核人拒絕（填原因）→ 已退回 → 編輯後重送 → 核准 → 作廢。
9. 建單 → 送簽 → 建單人撤銷 → 已退回 → 重送。
10. 已核准後由最後一關簽核人作廢；確認作廢後不可編輯、刪除、重送，且可另開同一出差人同日期的新單。
11. 重疊檢查：同一出差人兩張日期相鄰（不重疊）、同日、被包住的有效單，確認相鄰可送簽、其餘被擋並列出衝突單號與日期。
12. 通用簽核端點（`ApprovalController`）對出差單的送簽、核准、拒絕、撤銷、作廢五個動作都回錯誤，簽核進度查詢不被擋。

**D. 可見範圍與列表（真實資料庫）**
13. 一般使用者只看到自己建立、自己出差與待自己簽核的單；簽核人可檢視自己簽核的單但不能編輯；有「出差單管理」者看得到全部，但看不到他人單據的編輯、送簽等按鈕。
14. 列表篩選：單號關鍵字、出差人、狀態（含「草稿」）、日期區間（邊界日算有交集）、「待我簽核」，以及組合、分頁、預設起日由新到舊。
15. 確認出差人下拉選單是否包含離職員工（會影響離職出差人的單能否用出差人篩選）。
16. 確認出差人對應員工的推測：目前以 `User.Account` 等於 `t_1000Staff.Account` 比對；若實際關聯不是這樣，可見範圍與預設出差人都會錯。

### 已知缺口與待使用者決定（來自各 ticket 實作回報）
- **角色簽核模式拒絕不了：** 引擎 `RejectApproval` 要求紀錄的 UserId 等於操作者，角色簽核的待簽紀錄沒有 UserId。出差單若設成指定角色簽核，簽核人無法拒絕（領料單等亦同）。引擎缺陷，未修，是否另開 ticket 待決定。
- **ticket 06 修改了共用引擎 `VoidApproval`：** 作廢只看最近一輪送簽之後的紀錄（修正「拒絕後重送再核准，作廢被舊紀錄擋住」）。影響領料單、進貨單、請假單、公文的作廢檢查（沒重送過的單行為不變）。請使用者確認接受，並注意它假設同一輪紀錄的 Id 遞增，需在 SQL Server 確認。
- **重疊檢查與送簽之間沒有鎖：** 兩張單據同時送簽理論上都可能通過，未做唯一性約束或鎖。是否要加待決定。
- **舊資料：** 修正前已核准的角色模式單據，紀錄沒有簽核人，仍無人能作廢。
- **引擎既有行為（未改）：** 拒絕後重送，簽核進度會新舊兩輪交錯；角色模式同關需多人時同一人可重複簽；「待我簽核」在同關多人時，前一關只要有一筆核准就算輪到。
- **`ApprovalService.cs` 內有一份疑似無人使用的舊重複實作**，未動，是否清理待決定。
- **簽核人不需要「出差單」功能權限：** 為了讓簽核人能檢視與簽核，`Index`、`Get`、核准、拒絕、作廢端點未掛功能權限，可見範圍由服務依登入者與簽核紀錄限縮。
- **一般列表不含「曾簽過但已不輪到」的單**（依 spec Q10 字面）；列表上沒有操作按鈕，只在檢視頁操作。
- **前端沒有「目前是管理者、顯示全部」的提示**，後端沒有回傳此旗標。
- **權限檢查方式：** 「出差單管理」由服務直接查 Permission 表（權限變更即時生效），與其他功能讀 JWT 的方式不同；若要一致，需改 `ICurrentUserService`。
- **前端只通過 `vite build`，所有畫面與操作都未在瀏覽器實際驗證**，包括送簽、核准、拒絕、撤銷、作廢按鈕與確認提示、篩選與日期區間清除。
- **`http.js` 被修改**（加入自動帶 `Authorization` 的 interceptor，baseURL 仍寫死 `localhost:7129`）。
- 權限項目編號 1060（出差單）、1061（出差單管理）為 agent 依現有編號推定，請確認不與其他用途衝突。
