# 出差單（出差事前申請與簽核）

Status: resolved

> 實作完成於 `feat/business-trip`（ticket 01–07，2026-10-20）；ticket 08（真實環境驗證與上線準備）暫緩，已知缺口與待決定事項記錄在該 ticket 的 Comments。

相關文件：`GLOSSARY-MAP.md`（差勤 context，術語以 `docs/attendance/GLOSSARY.md` 為準）、`docs/attendance/adr/0001`（出差單狀態由自己維護、簽核動作走專屬端點）、`docs/adr/0001`（領料單的同一做法，本規格比照其結構）。

## Problem Statement

員工因公前往公司以外的地點時，目前系統沒有任何單據可以申請與留存。出差只能靠口頭或外部管道告知，主管無從簽核、行政無從彙整，事後也無法查詢「某人哪幾天去了哪裡、為什麼」。

現有的請假單與簽核引擎也無法直接套用：簽核引擎只記錄簽核紀錄，不維護單據狀態（拒絕與撤銷沒有鉤子，撤銷與作廢都把紀錄標成同一個狀態），請假單的 `ApprovalStatus` 欄位更從未被更新；引擎的撤銷檢查另有缺陷（見 Implementation Decisions 的前置修正）。

## Solution

提供**出差單**：有權限的人建立出差單，指定**出差人**、出差地點、出差事由、出差起訖日，選填客戶與備註，送出簽核；簽核全部通過後單據為已核准。已核准的出差單若行程取消，可由最後一關簽核人**作廢**。

出差單有五個**出差單狀態**：草稿、簽核中、已核准、已退回、已作廢，由出差單自己維護。送簽時檢查同一位出差人在日期上不可有重疊的有效出差單（簽核中或已核准）。一般使用者只看到自己建立、自己出差或待自己簽核的出差單；有管理權限者可看全部。簽核人可在出差單列表篩選「待我簽核」，並在檢視頁核准或拒絕。

本次只做事前申請與簽核，不含費用報支、匯出與通知。

## User Stories

### 建立與維護出差單

1. 身為建單人，我想建立一張出差單，以便記錄一次出差的申請。
2. 身為建單人，我想選擇出差人（在職員工），以便主管或行政代填時仍能記錄實際前往出差的人。
3. 身為建單人，我想預設出差人為我自己，以便自己申請時少選一個欄位。
4. 身為建單人，我想填寫出差地點，以便簽核人知道要去哪裡。
5. 身為建單人，我想填寫出差事由，以便簽核人判斷是否核准。
6. 身為建單人，我想填寫出差起日與迄日，以便記錄出差的期間；起迄可為同一天。
7. 身為建單人，我想起日可以早於今天，以便先出差、回來才補單。
8. 身為建單人，我想在迄日早於起日時被擋下並看到明確訊息，以便不會存出不合理的期間。
9. 身為建單人，我想選填客戶（從現有客戶主檔挑選），以便出差與客戶有關時能追溯。
10. 身為建單人，我想選填備註，以便說明特殊情況。
11. 身為建單人，我想看到依起訖日計算的出差天數（日曆天、含起訖兩天、不扣假日），以便確認期間沒填錯。
12. 身為建單人，我想建立時自動取得單號（`BT` + 民國年月 + 三位流水），以便每張出差單都有唯一編號。
13. 身為建單人，我想新建的出差單先是草稿，以便慢慢填寫、尚未送簽前都能修改。
14. 身為建單人，我想編輯草稿狀態的出差單，以便修正填錯的內容。
15. 身為建單人，我想編輯已退回的出差單後重新送簽，以便處理簽核人的意見。
16. 身為建單人，我想刪除草稿狀態的出差單，以便清掉不需要的草稿。
17. 身為建單人，我想在出差單進入簽核中、已核准或已作廢後無法編輯或刪除，以便單據內容不會在簽核後被更動。
18. 身為建單人，我想被擋下時看到明確的錯誤訊息（例如「簽核中的出差單不可編輯」），以便知道原因。
19. 身為建單人，我想選擇出差人時只看到在職員工，以便不會選到已離職的人。
20. 身為建單人，我想已核准的出差單若要改日期或地點，只能作廢後重開，以便核准過的內容不被悄悄改掉。

### 送簽與簽核

21. 身為建單人，我想把草稿或已退回的出差單送出簽核，以便讓主管審核。
22. 身為建單人，我想在送簽時被告知與我指定的出差人日期重疊的有效出差單（顯示衝突的單號與日期），以便先調整再送。
23. 身為建單人，我想草稿階段不做重疊檢查，以便先保留草稿。
24. 身為建單人，我想已退回與已作廢的出差單不被當成有效單據參與重疊檢查，以便重開新單不會被舊單擋住。
25. 身為建單人，我想在沒有啟用的簽核設定時送簽，被告知「找不到啟用中的簽核設定」，以便知道要請管理者先設定流程，單據不會卡在半路。
26. 身為建單人，我想在簽核流程完成前撤銷送簽，以便發現錯誤時收回，撤銷後單據變成已退回。
27. 身為建單人，我想無論簽核是指定人員或指定角色，我都能撤銷自己送出的簽核，以便不受簽核設定方式影響。
28. 身為簽核人，我想在出差單列表篩選「待我簽核」，以便快速找到輪到我簽的出差單。
29. 身為簽核人，我想看到待我簽核的出差單內容（出差人、地點、事由、起訖日、天數、客戶、備註）與簽核進度，以便做出決定。
30. 身為簽核人，我想核准出差單，以便讓出差申請生效。
31. 身為簽核人，我想核准中間關卡時單據仍是簽核中，只有最後一關通過才變成已核准，以便狀態與簽核進度一致。
32. 身為簽核人，我想拒絕出差單並寫下原因，以便讓建單人知道為什麼被退回，拒絕後單據變成已退回。
33. 身為簽核人，我想未填拒絕原因時被擋下，以便建單人一定看得到理由。
34. 身為簽核人，我想還沒輪到我時無法核准，以便簽核順序不被跳過。
35. 身為簽核人，我想在核准或拒絕失敗時，簽核紀錄與出差單狀態一併回復，以便不會出現「簽核已存檔但單據狀態沒變」。
36. 身為最後一關簽核人，我想作廢已核准的出差單（例如行程取消），以便單據反映實際情況。
37. 身為最後一關簽核人，我想不論最後一關是指定人員或指定角色，我都能作廢自己核准過的出差單，以便不受簽核設定方式影響。
38. 身為建單人，我想作廢後的出差單不能再重送，以便保持歷史單據的完整性；要再出差就另開新單。
39. 身為建單人，我想無法透過通用簽核端點對出差單做送簽、核准、拒絕、撤銷、作廢，以便所有動作都經過出差單自己的邏輯。
40. 身為簽核人，我想仍能透過通用簽核進度查詢看到出差單走到哪一關，以便追蹤。

### 查詢與可見範圍

41. 身為一般使用者，我想在列表只看到我建立或出差人是我的出差單，以便不看到無關的單據。
42. 身為簽核人，我想在列表也看到待我簽核的出差單，即使我不是建單人或出差人，以便能處理。
43. 身為有管理權限的人，我想看到全部出差單，以便彙整與追蹤。
44. 身為使用者，我想用單號關鍵字、出差人、出差單狀態與日期區間篩選出差單，其中日期區間以「與出差起訖有交集」為準，以便找到某段期間內的出差。
45. 身為使用者，我想列表預設依出差起日由新到舊排序並分頁，以便最近的出差排在前面。
46. 身為使用者，我想開啟一張出差單時看到完整內容與目前的出差單狀態，以便知道它現在能做什麼。
47. 身為使用者，我想在單據不可編輯時（簽核中、已核准、已作廢）同一頁以唯讀方式檢視，以便不用另外找檢視入口。

### 權限與設定

48. 身為管理者，我想有「出差單」功能權限的人才能建單，以便控管誰能開單；建單時可代填出差人。
49. 身為管理者，我想用現有的簽核設定建立一組啟用的「出差單」簽核流程（指定人員或指定角色皆可），以便不用改程式就能調整關卡。
50. 身為管理者，我想同時有多組啟用的出差單簽核設定時，送簽被擋下並提示設定重複，以便先修正設定。

## Implementation Decisions

- **前置修正（獨立 ticket，先於出差單）：簽核引擎的撤銷與作廢檢查。** 依目前讀到的程式：撤銷檢查的是「最後一關那筆待簽紀錄的簽核人是否為操作者」，而不是送簽人，所以建單人撤不了，角色簽核模式（該筆紀錄沒有 UserId）任何人都撤不了；核准時引擎也沒有把操作者記到角色簽核的紀錄上，作廢檢查「只能作廢自己的簽核」因此在角色簽核模式失效。前置修正內容：撤銷改為驗證操作者是送簽人，且流程仍有待簽核的紀錄；核准時記錄實際簽核人，使作廢檢查在兩種簽核模式都能運作。此修正在共用引擎，領料單、進貨單、請假單、公文同受影響，需用真實引擎（非假引擎）撰寫測試覆蓋兩種簽核模式。領料單現有測試使用假引擎，沒有覆蓋這個行為。
- **新增出差單單據類型**：單據類型列舉新增「出差單」（值 10），並新增對應的簽核目標處理器，供引擎確認單據存在；於簽核引擎的註冊處註冊。
- **出差單資料表**：單頭一張表，無明細表。欄位：單號、出差人、建單人、出差地點、出差事由、出差起日、出差迄日、選填客戶、選填備註、出差單狀態、建立時間。資料表須同步更新資料庫專案、實體模型，並依專案慣例提供既有資料庫的 SQL 腳本。
- **出差單狀態**：草稿、簽核中、已核准、已退回、已作廢，以列舉儲存。狀態流轉：草稿 → 簽核中（送簽）；簽核中 → 已核准（最後一關核准）／已退回（拒絕或撤銷）；已退回 → 簽核中（重送）；已核准 → 已作廢；已作廢為終態。中間關卡核准不改狀態。判斷「最後一關核准完成」以引擎回報流程完成為準。
- **簽核動作走出差單專屬端點**（依差勤 ADR-0001）：送簽、核准、拒絕、撤銷、作廢五個動作在出差單服務內，以單一資料庫交易包住「引擎動作 + 出差單狀態」，任一失敗整筆回滾。動作的前置狀態檢查在引擎動作之前進行（例如只有簽核中可撤銷、只有已核准可作廢），錯誤訊息包含目前狀態。通用 `ApprovalController` 對出差單的這五個動作回錯誤（行為與領料單相同）；簽核進度查詢與「待我簽核」查詢不擋。
- **送簽時的重疊檢查**：同一出差人、狀態為簽核中或已核准、日期區間（含起訖兩天）與本單有交集的出差單，視為衝突，排除本單自己；衝突時列出單號與日期並擋下送簽。草稿、已退回、已作廢不參與檢查。不檢查請假單與加班單。
- **欄位驗證**：出差人必須是在職員工；地點與事由必填；迄日不得早於起日；起日不設下限；客戶若填寫必須存在於客戶主檔。出差天數只在顯示時計算（迄日減起日加一），不存資料庫。
- **單號**：沿用現有流水號服務，前綴 `BT`，格式與領料單的民國年月加三位流水一致。
- **簽核設定**：不內建關卡，沿用現有簽核設定機制。沒有啟用設定或有多組啟用設定時，引擎已回對應錯誤，出差單服務原樣轉出。上線步驟：由管理者或開發者以現有 API 建立一組啟用的出差單簽核設定（目前前端沒有設定畫面）。
- **權限**：新增兩個功能權限項目——「出差單」（可建單、編輯、送簽、檢視自己的單）與「出差單管理」（可檢視全部）。簽核人不需要額外權限，由簽核紀錄決定能否簽核。權限項目依現有 Permission 機制設定。
- **列表可見範圍與查詢**：一般使用者看到建單人或出差人為自己的單，加上待自己簽核的單；管理權限看全部。篩選條件為單號關鍵字、出差人、出差單狀態、日期區間（與出差起訖有交集）；「待我簽核」篩選取自引擎現有的待簽核查詢並限定出差單。預設依起日由新到舊，沿用專案現有分頁與排序寫法。列表查詢無法由記憶體資料庫驗證，須在真實資料庫確認。
- **前端**：出差單列表頁（查詢、新增、進入檢視，含「待我簽核」篩選），以及建立／編輯／檢視共用的一頁（編輯時有儲存草稿、送簽、撤銷、刪除；簽核中、已核准、已作廢為唯讀；輪到目前使用者簽核時顯示核准與拒絕；已核准且目前使用者為最後一關簽核人時顯示作廢）。新增路由與選單入口，簽核進度沿用現有簽核進度查詢。依專案前端規範撰寫。
- **文件**：術語與 ADR 已建立（見相關文件）；實作中若出現新術語，更新差勤的 `GLOSSARY.md`。

## Testing Decisions

- **好測試的標準**：只驗證對外可觀察的行為（回傳結果、單據狀態、資料庫內容），不驗證內部實作；一個測試對應一個使用者故事或規則。
- **主要接縫：出差單服務一個接縫。** 用服務層驗證建立、編輯、刪除、五個簽核動作的狀態流轉、前置狀態檢查、重疊檢查、欄位驗證、單號、可見範圍與列表查詢、失敗時整筆回滾。
- **前置修正 ticket 的接縫：真實簽核引擎。** 這是撤銷與作廢檢查的修正，必須用真實引擎配記憶體資料庫，覆蓋指定人員與指定角色兩種簽核模式；這是為此修正新增的接縫，與出差單服務接縫分開。
- **通用端點守門測試**：延伸現有守門測試，加上出差單五個動作被擋。
- **前例**：領料單服務測試（記憶體資料庫、假簽核引擎、假使用者、假流水號、種子資料）與通用簽核端點守門測試。
- **不做**：前端目前沒有任何自動化測試設定，本次不新增，前端靠手動驗證。
- **限制**：測試使用 SQLite 記憶體庫，不等於 SQL Server；列表查詢、日期區間比較與重疊檢查的查詢，須由使用者在真實資料庫驗證。

## Out of Scope

- 出差費用報支（核銷、發票、墊款、旅費），另案。
- Excel 匯出。
- 推播、Email 或任何通知。現況簽核引擎本來就沒有通知（`Notification` 資料表未被使用），之後若要做，應整個簽核引擎統一補。
- 請假單、加班單的衝突檢查。
- 跨單據類型的通用簽核中心（待簽清單、核准與拒絕畫面）。
- 簽核設定的管理畫面。
- 引擎補上拒絕與撤銷鉤子的重構（見 ADR）。
- 請假單沒有單據狀態的問題。
- 請假、加班用詞的術語整理。
- 前端自動化測試。

## Further Notes

- 「出差」的定義較寬：只要因公前往公司以外的地點即是，不要求過夜或跨縣市，所以當日往返也開出差單。不做獨立的外出單。
- 一張出差單只有一位出差人，多人同行各開一張。
- 前置修正若在實作中發現範圍超出預期（例如牽動既有領料單測試的假設），回來與使用者討論，不自行擴大。
- 簽核動作的錯誤訊息文字比照領料單的風格，包含目前狀態。
